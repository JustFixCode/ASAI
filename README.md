# ASAI production-oriented foundations — NOT READY FOR DEPLOYMENT

This is unfinished engineering work, not a production-grade trading system or a completed implementation of the ASAI blueprint. Do not use it with a real account, deploy it as an autonomous service, or trust it to manage money.

## Included components

- `risk/`: an isolated deterministic risk evaluator with unit tests. It is not connected to or an enforcement boundary for the broker adapter.
- `broker/`: a low-level, read-only Alpaca paper stocks evidence adapter, selected only as a development default. Its public create/submit and cancel methods are disabled unconditionally; operators must use the broker UI/console for cancellation. Its private request helper permits only exact `GET` requests to the fixed read paths used by the public lookup methods and rejects payloads. No actual broker test was performed. This is defense in depth, not a security authority: Python object internals are mutable, and anyone with raw credentials or a caller-held transport can use them outside this adapter.
- `db/`: PostgreSQL journal, safety-control, and paper-order-state migrations with SQL invariant tests. The paper-order model records paper-only order intent and lifecycle states; it has no broker credentials, network calls, or execution capability. These database artifacts are foundational only and have not been executed against PostgreSQL in this environment; do not use them without full review and database testing.
- `config/` and `memory/`: a deliberately narrow JSON-compatible YAML manifest loader and a local JSONL configuration-review history. The manifest loader reads only bounded, no-follow regular files. The audit helper rejects symlinks, non-regular files, wrong owners, non-`0600` permissions, invalid records, and crash-partial final lines; readers use a shared advisory lock and writers use an exclusive advisory lock. This local history is **not tamper-evident** and does **not** provide durable audit integrity: a sufficiently privileged local actor can deliberately truncate, rewrite, or replace it without reliable detection. Rejected partial logs require manual investigation/intervention; the helper never repairs them silently.
- `tests/`: Python unit tests using fake transports. Run from this folder with `python -m unittest discover -s tests -v`.

## Critical gaps

There is no integrated risk boundary or service binding verified risk decisions to broker orders, no controlled execution path, no live trading, no real market feed, no forex or crypto broker, no complete survival protocol, no strategy/AI, no dashboard, no production security, monitoring or deployment system. Reconciliation code and the database paper-order lifecycle are foundational components only: they are not connected to broker execution, cannot submit, route, cancel, or fill real orders, and do not make this a running trader or production system. The Python and SQL tests do not verify real broker compatibility, database correctness, trading safety, or production readiness. API/venue rules can change and must be checked against current official documentation.

Before live trading: specify the jurisdiction, markets and intended broker/exchange for each asset class; run PostgreSQL and broker integration, adversarial security, concurrency and recovery tests; implement and independently review the atomic risk-to-order control boundary, reconciliation, permission isolation, audit, monitoring and kill-switch procedures; obtain appropriate legal/regulatory and financial review; and obtain the owner's explicit approval. No credentials are included. Do not paste credentials in chat.
